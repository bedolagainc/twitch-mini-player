# Mini Twitch Player (Rust)

Мини-плеер для просмотра стримов Twitch без открытия браузера.  
Написан на Rust с использованием `eframe` + `egui` (GUI) и `streamlink` (извлечение HLS-ссылок). Видео воспроизводится напрямую через **`libmpv`** и рисуется внутри окна egui как текстура.

## Возможности
- Нативное окно (не браузер, не Electron)
- Выбор качества потока: **«Авто»** (уровень подбирается по замеренной скорости сети) либо любой вариант, который реально есть на текущем стриме (список берётся из ответа `streamlink`; алиасы `best`/`worst` скрыты — они дублируют реальные варианты)
- Управление мышью поверх видео: **колесо — громкость**, **клик — пауза** (при снятии с паузы — сразу к эфиру), **двойной клик — полный экран только для видео** (слайдера громкости поэтому нет)
- **Избранные каналы**: звёздочка у поля канала добавляет/убирает канал, правый клик по кнопке избранного убирает его из списка
- Получение прямой HLS-ссылки через `streamlink`
- Воспроизведение через `libmpv` прямо внутри окна (без отдельного нативного окна)
- Плавные скруглённые углы видео и меню, которое рисуется поверх кадра
- **Кадр не растягивается**: пропорции берутся у mpv (`video-params/aspect`), поэтому при развороте окна или смене размера остаются чёрные поля, а картинка сохраняет геометрию
- Метаданные стрима через официальный Twitch Helix API (тайтл, игра, зрители)
- **Сразу лучшие настройки**: GPU-декод, GPU-рендер и профиль отрисовки «Авто»
  включены по умолчанию — ничего настраивать не нужно
- **Консоль разработчика** (кнопка справа в строке канала): декод, профиль отрисовки,
  статистика, ссылка на поток, Client ID и метаданные — всё «техническое» в одном
  окне, чтобы не мешать обычному просмотру
- **Захват звука стрима для будущих субтитров** (эксперимент, Windows 11):
  WASAPI process loopback берёт звук только этого плеера, с индикатором уровня и
  записью 10 секунд в WAV для проверки — см. раздел «Субтитры с переводом»
- **Индикатор «в эфире / не в эфире»** у поля канала (красная/серая точка) — статус проверяется в фоне
- **Заставка буферизации**: пока mpv ждёт данные, поверх области видео вращается
  индикатор с подписью и секундами («Буферизация… 3 с», «Подключение… 1 с»)
- **Иконка в трее**: левый клик — показать/скрыть окно, правый — меню «Показать/Скрыть», «Играть/Остановить», «Выход»
- Качество **`audio_only`** (только звук): ~0.2 Мбит/с вместо 6–8 — игра не страдает, если смотреть/слушать стрим параллельно
- Всё состояние (канал, качество, громкость, настройки нагрузки, размер и место окна) сохраняется между запусками

## Требования
Перед сборкой установите в систему и добавьте в `PATH`:

1. **Rust** — https://rustup.rs/
2. **streamlink** — https://streamlink.github.io/
3. **`libmpv-2.dll`** — положите файл рядом с `.exe` (в `target\release\`).
   Берётся из сборки mpv (https://mpv.io/installation/) или из готовых libmpv-сборок.

Проверка в терминале:
```powershell
streamlink --version
cargo --version
```

`libmpv-2.dll` должен лежать в одной папке с `twitch_mini_player.exe`. Программа ищет его рядом с `.exe`, в текущей папке и в `C:\Program Files\MPV Player\`.

## Client ID (Twitch API)
Чтобы видеть метаданные (тайтл, игру, количество зрителей), зарегистрируйте приложение на https://dev.twitch.tv/console/apps и вставьте **Client ID** в поле «Twitch API» в консоли разработчика (кнопка **«Консоль»** в строке канала). Без этого плеер всё равно работает, но без метаданных.

## Сборка и запуск
```powershell
cd путь\к\twitch-mini-player
cargo build --release
cargo run --release
```
Готовый `.exe` будет в `target/release/twitch_mini_player.exe`.

## Встроенное видео (libmpv)
Видео рендерится внутри окна egui через Render API libmpv. Основной путь —
OpenGL (`GPU-рендер`, включён по умолчанию): mpv масштабирует кадр силами
видеокарты и отдаёт готовую текстуру. Запасной путь — программный
(`MPV_RENDER_API_TYPE_SW`): кадр отдаётся в память и загружается в текстуру egui.
В обоих случаях кадр имеет плавные скругления углов и всегда находится под
элементами интерфейса (меню, кнопки, чипы состояния).

Параметры mpv задаются в коде (`src/libmpv.rs`): `vo=libmpv`, `video-timing-offset=0`,
`hls-live-edge=1`, умеренный буфер (`cache-secs=12`, `cache-pause-initial=no`,
`demuxer-max-bytes=32MiB`, `demuxer-max-back-bytes=4MiB`, `network-timeout=30`),
а также `sub-auto=no` и `audio-file-auto=no` (не тратим запросы на поиск
внешних субтитров и аудиодорожек в HLS).
Аппаратное декодирование и GPU-рендер включаются по умолчанию; переключатели
живут в консоли разработчика (см. раздел про нагрузку).

Ориентация кадра в программном пути: mpv отдаёт строки в порядке OpenGL
(строка 0 буфера — **низ** кадра), поэтому `libmpv::render` переставляет строки
при упаковке в `ColorImage`. Это делает картинку одинаковой в обоих путях и не
зависит от сборки mpv: `MPV_RENDER_PARAM_FLIP_Y` не используется вовсе.

## GPU-рендер кадра (включён по умолчанию)
Обычный путь: mpv **программно** масштабирует кадр в буфер `rgb0`, плеер превращает
его в `Color32` и загружает мегабайты в текстуру — два прохода по кадру на ЦП.
GPU-путь (`MPV_RENDER_API_TYPE_OPENGL` + `egui::PaintCallback`, `src/gpu.rs`)
убирает их полностью:

- mpv рендерит кадр **прямо в OpenGL-текстуру** своего FBO — без копий через RAM;
- egui рисует готовую текстуру квадом, скругления углов считает шейдер;
- масштабирование делает видеокарта (шейдеры mpv), поэтому картинка резче,
  и профиль отрисовки больше не уменьшает разрешение кадра (до 1920×1080).

Требуется OpenGL 3.3 (есть на любой видеокарте последних ~15 лет). Если контекст
создать не удалось (старый драйвер, RDP-сессия), плеер автоматически возвращается
на отрисовку в ЦП и пишет причину в строку ошибки — ничего вручную переключать не надо.

Ориентацию кадра плеер контролирует сам, без `MPV_RENDER_PARAM_FLIP_Y`
(на разных сборках mpv он ведёт себя по-разному — отсюда и была «перевёрнутая»
картинка). Кадр и в OpenGL-текстуру, и в программный буфер приходит
**сверху вниз** (строка 0 — верх картинки), поэтому:

- GPU-путь: шейдер берёт UV как есть, без переворота;
- программный путь: строки копируются в том же порядке.

Проверено скриншотами обоих путей против кадра, который mpv сам записывает
в PNG (`mpv --frames=1 --of=image2`): любая попытка «перевернуть» даёт
картинку вверх ногами. Настройки переворота в интерфейсе нет.

Замеры (синтетический поток 1280×720, окно 760×720, один и тот же `.exe`,
время ЦП за 12 секунд воспроизведения):

| режим | ЦП | память |
|---|---|---|
| программный путь до v0.12 (перерисовка по таймеру) | 29,8 с | 148 МБ |
| программный путь (v0.13, перерисовка по кадрам) | 6,6 с | 148 МБ |
| **GPU-рендер (v0.13)** | **2,0 с** | 257 МБ |
| окно свёрнуто или скрыто в трей | ≈ 0 | 80 МБ |

GPU-режим экономит ЦП, но занимает больше памяти (текстуры и GPU-бэкенд mpv).
Переключатель живёт в консоли разработчика: обычному просмотру он не нужен.

**Нужно ли включать GPU-декод и GPU-рендер одновременно?** Да, это правильная
комбинация, они делают разную работу: декод снимает с ЦП разбор H.264, рендер —
масштабирование и загрузку кадра. При этом один проход через RAM остаётся:
на Windows zero-copy `d3d11va → OpenGL` для Render API недоступен, поэтому mpv
работает в `hwdec=auto-copy` (декод на GPU, копия в системную память), а дальше
кадр уже попадает в GL-текстуру. Копию делает DMA-движок, а не ядро ЦП, так что
это дешевле программного пути в разы. Полностью zero-copy возможен только с
`gpu-api=d3d11`, но тогда mpv не сможет рисовать в FBO окна egui (OpenGL).

## Свёрнутое окно и трей
При сворачивании или скрытии окна в трей плеер выключает видеодорожку (`vid=no`):
звук продолжается, а ЦП почти не тратится (кадры не рендерятся вовсе).
При восстановлении окна видео включается обратно, картинка берётся из буфера.

Иконка в трее: **левый клик** — показать/скрыть окно, **правый клик** — меню
«Показать/Скрыть», «Играть/Остановить», «Выход». Подсказка при наведении
показывает канал, качество и состояние. Иконку можно отключить в `settings.json`
(`"tray": false`), тогда же перестаёт работать скрытие окна в трей.

## Консоль разработчика
Кнопка **«Консоль»** справа в строке канала открывает отдельное окно — всё
«техническое» собрано там и по умолчанию закрыто:

- **Декодирование и отрисовка** — «GPU-декод (hwdec)», «GPU-рендер (OpenGL)» и
  профиль отрисовки: «Авто (по нагрузке ПК)», «Высокое (60 FPS)»,
  «Сбалансированное», «Экономное (30 FPS)». В режиме «Авто» рядом показано, какой
  профиль выбран сейчас;
- **Диагностика** — строка статистики (см. ниже);
- **Поток** — прямой HLS-URL, кнопка «Копировать ссылку», тайтл/игра/зрители;
- **Twitch API** — поле Client ID;
- **«Лучшие настройки»** — одним нажатием возвращает GPU-декод, GPU-рендер,
  «Авто»-отрисовку и авто-качество (минимум нагрузки и задержки).

Обычные настройки ничего не требуют: при первом запуске (и после обновления
схемы настроек) включаются именно «лучшие» значения.

## Строка статистики
В консоли разработчика, в блоке «Диагностика», выводится компактная строка:

```
UI 59 к/с · видео 60 к/с · 1920×1080 → 1920×1080 · буфер 11.8 с · декод d3d11va-copy · GPU-кадры 1024 · отрисовка Высокое (60 FPS)
```

- `UI` — сколько раз в секунду перерисовывается интерфейс (в покое это 1 к/с:
  окно не будится, пока нет нового кадра);
- `видео` — фактический FPS потока по данным mpv;
- `1920×1080 → 1488×848` — разрешение потока и размер кадра, который реально
  рендерится (в GPU-режиме и в «Высоком» профиле они совпадают);
- `буфер` — запас времени вперёд; `декод` — фактический режим декодирования;
- `отрисовка` — профиль, которым плеер рисует кадр прямо сейчас (в «Авто» он
  подбирается сам);
- `потеряно` — сколько кадров mpv не успел показать (обычно 0);
- в режиме «Авто» добавляются `сеть 4.8 Мбит/с` (медиана замеров) и `авто→720p60`
  (к какому уровню ведёт текущая скорость).

Строка собирается не чаще двух раз в секунду, поэтому на нагрузку не влияет.

## Управление мышью
Слайдеров и кнопок поверх кадра нет — всё делается мышью над видео:

| действие | что делает |
|---|---|
| колесо над видео | громкость ±5% (чип «Громкость N%» поверх кадра) |
| одиночный клик по видео | пауза / продолжить (чип «Пауза») |
| двойной клик по видео | **полный экран только для видео** — интерфейс скрывается, кадр занимает весь экран |
| `Esc` | выйти из полного экрана (или повторный двойной клик) |
| правый клик по кнопке избранного | меню «Убрать из избранного» |

Одиночный клик применяется через 250 мс — так первый клик двойного не ставит
паузу «на полпути». Выбранная громкость сохраняется между запусками.

Снятие с паузы не продолжает с того же кадра (иначе картинка отставала бы от
эфира на всё время паузы), а **перескакивает к актуальному эфиру**: у live-HLS
`duration` — это длина seekable-окна, поэтому плеер прыгает в `100%`
(`seek 100 absolute-percent`), а если длительность неизвестна — в конец буфера
(`demuxer-cache-time`, документированное свойство mpv). Если ссылки нет вовсе
(например, поток из `TW_DEMO_URL` без live-окна), перескок просто не выполняется.

Полный экран видео — это именно «стрим на весь экран»: настройки и консоль
разработчика не рисуются, кадр вписывается в экран с сохранением
16:9 (чёрные поля по краям, если пропорции монитора другие), скругления
отключаются. Геометрия окна в этом режиме не сохраняется — после выхода плеер
открывается в прежнем размере. Для проверки раскладки без кликов есть
отладочный запуск `TW_VIDEO_ONLY=1`.

## Заставка и заглушка
Пока mpv не может показать кадр, поверх области видео крутится индикатор
с подписью и временем ожидания:

- «Подключение… N с» — идёт разрешение потока через `streamlink`;
- «Загрузка потока… N с» — ссылка получена, ждём первый кадр;
- «Буферизация… N с» — кэш опустел и mpv сам приостановил воспроизведение.

Заставка перерисовывается 12 раз в секунду, поэтому видно, что плеер жив, а не
«завис». Когда ничего не играет (или выбран `audio_only`, или канал не в эфире),
в области видео остаётся тёмный фон и подпись состояния («Область плеера»,
«Канал не в эфире», «Только звук»).

## Сохранение настроек
Состояние пишется в `%APPDATA%\twitch_mini_player\settings.json`: последний канал,
качество (включая режим «Авто»), громкость, профиль отрисовки, «GPU-декод»,
«GPU-рендер», «Трей», «Поверх окон», Client ID, версия схемы настроек,
размер и позиция окна. При следующем запуске всё открывается как было. Файл
читается «мягко»: отсутствующие поля берут значения по умолчанию, поэтому настройки
старых версий продолжают работать. Если версия схемы в файле ниже текущей,
«разработческие» настройки (декод, отрисовка, авто-качество) сбрасываются на
лучшие значения по умолчанию, а канал, громкость и геометрия окна сохраняются.
Избранные каналы лежат рядом, в `favorites.txt`.
Запись идёт с задержкой (не чаще раза в 1.5 с) и в момент закрытия окна, поэтому
она не мешает вводу.

Список в выпадающем меню формируется из ключей `streams` в JSON-ответе `streamlink`,
поэтому недоступных на стриме вариантов там нет (до первого запуска показывается
базовый набор-подсказка). Переключение выполняется **мгновенно**: новый HLS-URL
берётся из уже полученного ответа, повторный запуск `streamlink` не выполняется,
картинка меняется без остановки плеера.

## Отзывчивость и скорость подключения
- `streamlink` и запрос метаданных Twitch выполняются в **фоновом потоке**, поэтому
  интерфейс не зависает: окно продолжает перерисовываться, кнопка Play на время
  подключения блокируется (доступна «Отмена»), повторные клики игнорируются.
- Результат разрешения потока **кэшируется на 15 минут** для текущего канала:
  повторное нажатие Play и смена качества в этом окне происходят мгновенно.
  Если ссылка всё-таки истекла, плеер сам получит свежую и продолжит воспроизведение.
- Работает **спекулятивная предзагрузка**: как только вы ввели ник канала или
  кликнули по избранному, разрешение запускается в фоне — Play срабатывает сразу.
- Пока играет один канал, при смене ника рядом с «Остановить» появляется
  «Воспроизвести»: переключение выполняется одним кликом, без промежуточной остановки.
- Для ускорения старта используется `streamlink --twitch-disable-ads` (реклама в
  HLS сильно тормозит запуск), а в mpv выставлен `hls-live-edge=1` — по умолчанию
  mpv начинает воспроизведение с 3-го сегмента от live-edge, что добавляет ~4–6 с.
- Если `streamlink` не ответил за 45 секунд, подключение автоматически прерывается
  с сообщением о таймауте.

## Нагрузка на ЦП и память
- **Перерисовка по кадрам потока.** Кадры больше не «выпрашиваются» таймером: mpv
  сам будит окно, когда готов новый кадр (`mpv_render_context_set_update_callback` →
  `egui::Context::request_repaint`). Раньше интерфейс мог перерисовываться сотни раз
  в секунду вхолостую — после перехода на событие «есть кадр» нагрузка упала
  примерно в 5–6 раз при той же плавности.
- **GPU-декод** (включён по умолчанию, переключатель в консоли): mpv работает в
  режиме `hwdec=auto-copy` — кадр декодируется видеокартой, а затем копируется в
  память. Если подходящего декодера нет, mpv сам откатывается на софт; фактический
  режим видно в строке статистики (`декод d3d11va-copy` / `декод софт`).
- **Профиль отрисовки** («Отрисовка» в консоли): «Авто (по нагрузке ПК)» — по
  умолчанию. В программном пути «Авто» берёт «Сбалансированное» (0.85 от разрешения
  окна), а если кадр интерфейса стал дольше 14 мс — «Экономное (0.65 + лимит
  30 кадров/с)». С GPU-рендером кадр почти бесплатен, поэтому «Авто» всегда рисует
  полное разрешение. Явно выбранный профиль не переопределяется.
- **Стабильный размер кадра**: сторона кадра округляется вверх до кратности 8,
  чтобы колебания вёрстки на 1–2 пикселя не вызывали пересоздание текстуры
  и повторный рендер.
- **Упаковка кадра** (программный путь): кадр `rgb0` превращается в `Vec<Color32>`
  одним проходом `chunks_exact` (ровно один `Color32` на пиксель).
- **Память**: кэш демуксера ограничен 32 МБ вперёд и 4 МБ назад — это ~12 с даже для
  1080p60 (8 Мбит/с ≈ 12 МБ), а по умолчанию mpv держит до 150–200 МБ. Отдельно
  ~119 МБ занимает сама `libmpv-2.dll`.

## Плавность на слабом интернете (буфер и качество «Авто»)
Задача: при той же скорости интернета не терять качество и не замирать.
- **Умеренный буфер** (`cache-secs=12`): плеер держит ~12 с запаса вперёд. Короткие
  просадки Wi-Fi/соседнего трафика не вызывают остановок — картинка едет из
  буфера, пока сеть догоняет. Старт не задерживается (`cache-pause-initial=no`),
  а память ограничена байтами (32 МБ), а не временем.
- **Догон эфира**: буфер — это запас на просадки, а не постоянное отставание. Если
  запас разросся (сеть проснулась после просадки) до 8+ с, плеер прыгает вперёд по
  **уже скачанным** данным (`seek` на запас минус 4 с), поэтому прыжок мгновенный и
  без сети. Не чаще раза в 10 секунд, чтобы картинка не «дёргалась»; на паузе и во
  время буферизации не догоняем.
- **Заставка буферизации**: если кэш всё-таки опустел, поверх кадра вращается
  индикатор с подписью «Буферизация… N с» — видно, что плеер жив и ждёт сеть.
- **Самовосстановление**: если остановка длится больше 12 секунд, плеер сам
  переразрешает поток (свежий CDN-узел) и продолжает с тем же качеством.
  Не чаще одного раза в 5 минут, чтобы не было «пинг-понга».
- **«Авто»** (пункт в списке качества, выбирается по умолчанию):
  уровень подбирается по **замеренной скорости сети** — mpv отдаёт
  `demuxer-cache-state/raw-input-rate` (байт/с), берётся медиана последних замеров
  (одиночные рывки HLS не считаются), и выбирается максимальный уровень, который
  проходит с запасом 35%. Шаг — один уровень за раз, не чаще раза в 30 с:
  вниз после двух замеров подряд (≈4 с) или сразу при пустом кэше, вверх — после
  30 с стабильной работы. Первые 10 секунд после старта качество не трогается
  (кэш только заполняется). Если `raw-input-rate` недоступен (старая сборка mpv),
  остаётся только реакция на просадки — «Авто» не ломается.
- **Прогноз просадки**: раз в 2 секунды снимается запас буфера. Если он за несколько
  замеров упал с 4+ с до <2 с, качество снижается **до** того, как картинка замрёт —
  просадка видна по тренду раньше, чем наступает остановка.

## Субтитры с переводом на русский (0.18.0: захват звука)
Цель: понимать англоязычных стримеров без знания языка. Всё считается **локально
и бесплатно**, без ключей API, аккаунтов и VPN.

Конвейер: **звук → распознавание речи → перевод → строка поверх видео**.

- **Звук только нашего плеера.** Захват идёт через Windows *process loopback*
  (`ActivateAudioInterfaceAsync` + `ProcessLoopbackMode=includetree`), поэтому в
  субтитры не попадает музыка из браузера, звуки игры или уведомления. Требуется
  Windows 10 build 20348+ (фактически Windows 11); на более старых системах —
  обычный системный loopback, то есть «весь звук компьютера».
- **Распознавание** — `whisper.cpp` с моделью только для английского
  (`ggml-base.en-q5_1` ≈ 60 МБ или `ggml-small.en-q5_1` ≈ 180 МБ). Модель `.en`
  точнее и быстрее многоязычной при том же размере, потому что язык не угадывается.
- **Фильтрация мусора** (три уровня): Silero VAD внутри whisper.cpp (`--vad`,
  модель ≈ 2 МБ) отбрасывает тишину и музыку без речи; принудительный
  `--language en` и `-sns` (подавление неречевых токенов) убирают «галлюцинации»
  вроде «Спасибо за просмотр» на тишине; короткие сегменты (< 3 слов) не показываются.
- **Перевод** — `opus-mt-en-ru` в int8 ONNX (encoder 51.5 МБ + decoder 58.7 МБ,
  всего ≈ 110 МБ) через ONNX Runtime. Полностью офлайн, ~0.1–0.3 с на фразу.
- **Синхронизация**: захваченный звук — это ровно то, что играет сейчас, поэтому
  субтитр привязывается к `time-pos` видео и появляется над «своей» речью даже при
  буфере 12 с и догоне эфира.
- **Задержка** ≈ 1–2.5 с от конца фразы (VAD-пауза + распознавание + перевод).
  Меньше — только у платных потоковых сервисов распознавания.
- **Вес** ≈ 190 МБ (base.en) или ≈ 310 МБ (small.en) вместе с моделями перевода и
  библиотекой ONNX Runtime; модели скачиваются кнопкой в консоли, а не входят в `.exe`.

### Как это ставится
Движок (DLL) лежит рядом с программой, модель — в профиле пользователя, поэтому
обновление плеера не затирает модели и не требует прав администратора:

```powershell
# движок + модель base.en (по умолчанию), всего ~70 МБ
powershell -ExecutionPolicy Bypass -File scripts\fetch-whisper.ps1

# только движок (10.7 МБ), модель поставить позже
powershell -ExecutionPolicy Bypass -File scripts\fetch-whisper.ps1 -Model none

# точнее, но тяжелее (~200 МБ)
powershell -ExecutionPolicy Bypass -File scripts\fetch-whisper.ps1 -Model small
```

Скрипт фиксирует версию сборки (`whisper.cpp` build `b5907`) и SHA-256 каждого
файла: недокачанный архив не превратится в «молчаливое падение при
инициализации». Из архива берутся только `whisper.dll`, `ggml.dll`,
`ggml-base.dll` и CPU-бэкенды `ggml-cpu-*.dll` — SDL2, CUDA-пакеты на 766 МБ
и примеры не нужны. Модели также доступны с зеркала `hf-mirror.com`, если
Hugging Face недоступен.

Этапы: `0.18.0` — захват звука процесса (**готово**, см. ниже); `0.19.0` —
английские субтитры с синхронизацией и перевод; `0.20.0` — настройки субтитров
в консоли (модель, VAD, размер шрифта); `0.21.0` — офлайн-тюнинг (сокращение
длинных фраз, словарь имён).

### Что уже работает в 0.18.0
Захват звука включается в консоли разработчика (кнопка **«Консоль»** в строке
канала) — галочка «Захватывать звук стрима (эксперимент)». Рядом:

- **индикатор уровня** — видно, что звук действительно приходит и что он
  не «висит» на нуле;
- **строка статистики** — `48.0 кГц, 2 кан → 16 кГц моно · 12.3 с · вытеснено 0`;
- **«Записать 10 с в WAV»** — файл `%APPDATA%\twitch_mini_player\capture.wav`.
  Откройте его любым плеером: слышен только стример, без музыки из браузера и
  звуков системы. Это и есть главная проверка process loopback.

Захват работает только на Windows 11 (build 20348+): у более старых систем нет
виртуального устройства `VAD\Process_Loopback`. Права администратора не нужны,
интернет не используется — звук не покидает компьютер.

## Структура проекта
| путь | что внутри |
|---|---|
| `src/main.rs` | окно, настройки, строка канала, консоль разработчика, буферизация |
| `src/libmpv.rs` | загрузка `libmpv-2.dll` и обёртка над Render API (кадры, свойства, события) |
| `src/gpu.rs` | GPU-рендер кадра: текстура OpenGL, шейдер, paint-колбэк egui |
| `src/tray.rs` | иконка и меню в системном трее |
| `src/subs.rs` | захват звука процесса (WASAPI process loopback) → 16 кГц моно |
| `scripts/fetch-whisper.ps1` | загрузка `whisper.cpp` (DLL) и моделей с проверкой SHA-256 |
| `CHANGELOG.md` | история версий и правило «изменение = версия» |

## Версии и CHANGELOG
Версия проекта — это единственный источник правды о том, что в сборке:
`Cargo.toml` → `env!("CARGO_PKG_VERSION")` → консоль разработчика и подсказка трея.
Все изменения фиксируются в `CHANGELOG.md` по разделам «Добавлено / Изменено /
Удалено / Исправлено».

- **patch** (`0.17.1`) — исправление, поведение не меняется;
- **minor** (`0.18.0`) — новая функция или UX; если появились поля в настройках,
  одновременно поднимается `SETTINGS_VERSION` и описывается миграция;
- **major** (`1.0.0`) — ломающее изменение: несовместимый `settings.json`,
  смена зависимостей или поведения по умолчанию.

## Диагностика падений
GUI-приложение не имеет консоли, поэтому при панике пишется файл
`%TEMP%\twitch_mini_player_crash.txt` (версия, текст паники, backtrace).

Подробный лог (события mpv, GPU-рендер, шаг перерисовки UI) включается переменной
окружения `TW_DEBUG_LOG=1` и пишется в `%TEMP%\twitch_mini_player_debug.txt`:

```powershell
$env:TW_DEBUG_LOG='1'; .\target\release\twitch_mini_player.exe
```

Проверка отрисовки без Twitch: `TW_DEMO_URL` запускает поток по указанной ссылке
(удобно и для GPU-режима, и для отладки на синтетике):

```powershell
$env:TW_DEMO_URL='av://lavfi:testsrc=size=1280x720:rate=30'
.\target\release\twitch_mini_player.exe
```

Отдельно есть ручной тест, который прогоняет реальный кадр через libmpv
(нужен `libmpv-2.dll` в `target\release\deps`):

```powershell
copy target\release\libmpv-2.dll target\release\deps\
cargo test --release -- --ignored --nocapture render_real_frame
# можно подставить свою ссылку:
$env:TW_TEST_URL='https://...m3u8'; cargo test --release -- --ignored --nocapture render_real_frame
```

## Оптимизация под слабый интернет
Выбирайте качество `480p30` или `audio_only` для минимального трафика.  
`1080p60` / `best` может потреблять 6–10 Мбит/с.

## Трафик, пинг и параллельная игра
Если Twitch открыт во время игры (CS2, Dota, любой сетевой шутер), высокий пинг —
это почти всегда не «нехватка скорости», а **переполнение очереди** на роутере:
HLS-сегменты скачиваются крупными кусками, очередь растёт, и пакеты игры стоят
в ней по 40–80 мс. Что помогает, по убыванию эффекта:

1. **`audio_only`** в списке качества: ~0.2 Мбит/с вместо 6–8. Разница для пинга
   радикальная — проверить можно за один клик.
2. **SQM / QoS на роутере** (`cake` или `fq_codel`), либо «Приоритет трафика» для
   игры: это лечит саму причину — очередь больше не копится.
3. **Провод вместо Wi-Fi** хотя бы для ПК: на Wi-Fi эфир и игра делят один канал.
4. Качество `480p30` вместо `1080p60` — куски меньше, очередь короче.
5. Не держать открытыми другие видео/загрузки: Steam-обновления забирают всю полосу.

Сам плеер сеть не «оптимизирует»: он буферизует ~20 с вперёд, а значит скачивает
сегменты заранее и рывками — это плата за отсутствие замираний.

## Важное примечание про рекламу
Twitch вставляет рекламу сервером прямо в HLS-плейлист (server-side ad insertion). Сторонний плеер не может «вырезать» её, не ломая поток. Эта программа делает акцент на легком клиенте и минимальном трафике, а не на обходе монетизации стримеров. Если хотите поддерживать создателей контента, используйте подписки, донаты или Twitch Turbo.
