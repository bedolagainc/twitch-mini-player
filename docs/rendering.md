# Видео, отрисовка и нагрузка

Как плеер выводит кадр и сколько это стоит. Всё включается само — раздел нужен,
только если хочется понять, что происходит под капотом.

## Два пути отрисовки

| путь | как работает | когда используется |
|---|---|---|
| **GPU (OpenGL)** | mpv рендерит кадр в OpenGL-текстуру своего FBO, egui рисует её квадом, скругления — в шейдере | по умолчанию; нужен OpenGL 3.3 |
| **программный** | mpv масштабирует кадр в `rgb0`, плеер пакует его в `Vec<Color32>` и загружает в текстуру | если контекст OpenGL создать не удалось (старый драйвер, RDP) |

Запасной путь включается сам, причина пишется в строку ошибки — переключать
вручную ничего не нужно.

Ориентация кадра: `MPV_RENDER_PARAM_FLIP_Y` не используется (на разных сборках
mpv он ведёт себя по-разному). Оба пути получают кадр сверху вниз, шейдер берёт
UV как есть. Проверено скриншотами против PNG, который mpv пишет сам
(`mpv --frames=1 --of=image2`).

Пропорции берутся у mpv (`video-params/aspect`), поэтому при развороте окна
остаются чёрные поля, а картинка не растягивается.

## Замеры

Синтетический поток 1280×720, окно 760×720, один и тот же `.exe`, время ЦП за
12 секунд воспроизведения:

| режим | ЦП | память |
|---|---|---|
| программный путь до v0.12 (перерисовка по таймеру) | 29,8 с | 148 МБ |
| программный путь (v0.13, перерисовка по кадрам) | 6,6 с | 148 МБ |
| **GPU-рендер (v0.13)** | **2,0 с** | 257 МБ |
| окно свёрнуто или скрыто в трее | ≈ 0 | 80 МБ |

GPU-режим экономит ЦП, но занимает больше памяти (текстуры и GPU-бэкенд mpv).

## Что включено по умолчанию

- **GPU-декод** — mpv работает в `hwdec=auto-copy`: декод на видеокарте, копия в
  память, дальше кадр попадает в GL-текстуру. Полный zero-copy на Windows
  недоступен: с `gpu-api=d3d11` mpv не смог бы рисовать в FBO окна egui (OpenGL).
  Фактический режим виден в строке статистики (`декод d3d11va-copy` / `декод софт`).
- **GPU-рендер** — см. выше.
- **Профиль «Авто (по нагрузке ПК)»** — в программном пути берёт
  «Сбалансированное» (0.85 от разрешения окна), а если кадр интерфейса стал
  дольше 14 мс — «Экономное (0.65 + лимит 30 кадров/с)». С GPU-рендером кадр
  почти бесплатен, поэтому «Авто» рисует полное разрешение.
- **Перерисовка по кадрам потока** — mpv сам будит окно
  (`mpv_render_context_set_update_callback` → `request_repaint`), в покое UI
  перерисовывается 1 раз в секунду.

Декод и рендер — разная работа, их правильно включать вместе: декод снимает с ЦП
разбор H.264, рендер — масштабирование и загрузку кадра.

## Строка статистики

В консоли, блок «Диагностика»:

```
UI 59 к/с · видео 60 к/с · 1920×1080 → 1920×1080 · буфер 11.8 с · декод d3d11va-copy · GPU-кадры 1024 · отрисовка Высокое (60 FPS)
```

| поле | смысл |
|---|---|
| `UI` | перерисовок интерфейса в секунду (в покое 1) |
| `видео` | фактический FPS потока по данным mpv |
| `1920×1080 → 1488×848` | разрешение потока → размер кадра, который реально рендерится |
| `буфер` | запас времени вперёд |
| `декод` | фактический режим декодирования |
| `отрисовка` | профиль, которым плеер рисует кадр прямо сейчас |
| `потеряно` | кадры, которые mpv не успел показать (обычно 0) |
| `сеть`, `авто→720p60` | только в режиме «Авто»: медиана замеров и целевой уровень |

Строка собирается не чаще двух раз в секунду.

## Память

Кэш демуксера ограничен 32 МБ вперёд и 4 МБ назад (~12 с для 1080p60). По
умолчанию mpv держал бы 150–200 МБ. Сама `libmpv-2.dll` занимает ~119 МБ.

## Свёрнутое окно и трей

При сворачивании или скрытии в трей плеер выставляет `vid=no`: звук идёт, кадры
не рендерятся. При восстановлении видео включается обратно.

Трей: левый клик — показать/скрыть, правый — меню («Показать/Скрыть»,
«Играть/Остановить», «Выход»). Иконка отключается в `settings.json`
(`"tray": false`) — тогда же перестаёт работать скрытие в трей.
